## 1. Executive summary

Архитектура скилла верная, и её ядро менять не нужно (§2). Проблемы — в трёх местах.

**Главный результат: цикл защищает от шума слабее, чем обещает.** При `--noise-sigma` по
умолчанию (0) правки без реального эффекта сохраняются в 74 % прогонов. Даже рекомендованные
документацией σ = 0,05–0,10 при шуме evaluator-а 0,05 оставляют такие правки в 48 % и 18 %
прогонов. Причина в постановке порога: Δ — разность двух шумных замеров, её разброс в √2 раз
больше шума одного замера, а champion — единичный удачный замер. Отчётный `best_score` при этом
завышен на 0,02–0,06 (R5).

**Второй результат: четыре заявленных контракта не выполняются.** Пробы показали:
- ошибка evaluator-а роняет цикл и оставляет непроверенную правку в файле (R1);
- `--git-isolation` при повторном запуске молча отключается и работа идёт на текущей ветке (R2);
- обещанный откат на LLM-грейдинг для не-Claude вендоров на деле — traceback (R3);
- два флага из документации не существуют (R4).

**Третий результат: отчётное число — это число настроечного набора.** Нет отложенной выборки
(R6) и финального подтверждающего замера (R7), хотя `SKILL.md` §5 сам называет его
единственной надёжной оценкой. Метрика для prompt и workflow — предсказание грейдера, а не
результат запуска (R9).

## 2. Что работает и менять не нужно

- **Неизменяемый harness с проверкой-подмножеством** (`before ⊆ after`) до и после применения:
  добавлять кейсы можно, менять и удалять существующие — нельзя.
- **Только структурированные форматы правок**, без raw-diff: правка не может выйти за пределы
  артефакта.
- **Решение принимает код, а не модель.** Tier считает скрипт (`measure_change_size.py`), а не
  Proposer.
- **Точный откат** из снапшота, а не «обратная правка».
- **Pairwise-гейт в обоих порядках** для прозы: сравнение пар верно, ничья оставляет champion.
- **Санация входа судьи** и рамка «текст — это данные».
- **Тестируемость:** инъекция `proposer` / `evaluator` / `decider` в `run_improvement_loop`
  позволяет гонять всю логику офлайн. Все новые проверки ниже строятся на этом же механизме.
- **Порядок проверки бюджета:** он проверяется до дорогого вызова evaluator-а.
- **Слияние только вручную:** цикл никогда не сливает ветку сам.

### R5 — Полоса шума: значение по умолчанию и неверная калибровка · P1 · M

**Код.** σ по умолчанию 0: `auto_improve.py:899` и `:115`. Документы (`SKILL.md:19`,
`metrics_reference.md:55`) рекомендуют σ ≈ 0,05–0,10 и тем самым приравнивают порог для

**Измерено** (проба E). Правки без реального эффекта; шум evaluator-а: нормальный,
sd = 0,05; 10 итераций, 300 прогонов на точку.

| σ | Пустых правок сохранено за прогон | Прогонов хотя бы с одной такой правкой | Завышение `best_score` |
| :--- | ---: | ---: | ---: |
| 0 (по умолчанию) | 1,28 | 74 % | +0,060 |
| 0,05 (= sd) | 0,56 | 48 % | +0,047 |
| 0,10 (2·sd) | 0,18 | 18 % | +0,024 |
| 0,12 (≈2,4·sd) | 0,13 | 13 % | +0,018 |
| 0,15 (3·sd) | 0,06 | 6 % | +0,010 |

**Почему так.**
- Δ — разность двух шумных замеров, её sd = √2·0,05 ≈ 0,071.
- Score champion-а — один удачный замер. Каждый KEEP поднимает планку на величину шума, и
  отчёт её наследует.

**Сделать.**
1. **Калибровка шума:** `--calibrate-noise K`, по умолчанию K = 3 для недетерминированных
   evaluator-ов и 0 для dataset.
   - K замеров baseline, по ним sd.
   - σ = z·√2·sd, z = 1,64 (≈ 2,3·sd).
   - sd и σ записывать в отчёт и в заголовок TSV.
   - Явный `--noise-sigma` имеет приоритет.
2. **Score champion-а = среднее K замеров.** После KEEP перезамерять кандидата (среднее K)
   вместо единичного значения, чтобы планка не росла на удаче.
3. **Исправить формулировки** в `SKILL.md:19` и `metrics_reference.md:55`: σ — порог для
   разности, а не шум одного прогона.
4. **Предупреждение** в stderr и в отчёте, если σ = 0 при недетерминированном evaluator-е.

**Приёмка.**
- Проба E с калибровкой (K = 3) даёт не более 10 % прогонов с сохранённой пустой правкой.
- Поведение dataset-режима не меняется: он детерминирован, σ = 0 для него корректно.

### R6 — Нет отложенной выборки · P1 · M

**Факт.** Цикл оптимизирует и отчитывается на одном и том же eval set. У skill-creator есть
стратифицированный `split_eval_set` (`skills/skill-creator/scripts/run_loop.py:37`). Сплит был
потерян вместе с отказом от вложенного `run_loop.py` (Rationalization Table в `SKILL.md`).

**Сделать.**
1. Флаг `--holdout F`: по умолчанию 0,4 для eval set от 10 кейсов; в dataset-режиме неприменим —
   там датасет и есть артефакт.
2. Итерации идут только на train-части.
3. Holdout оценивается дважды: baseline и финальный победитель. Не на каждой итерации — иначе
   переобучится и он.
4. Отчёт: train Δ и holdout Δ рядом; флаг `overfit_warning`, если holdout Δ ≤ 0 при
   train Δ > σ.
5. Переиспользовать `split_eval_set`: импортировать из skill-creator, как claude-backend уже
   находит `run_eval.py`, либо перенести в `common.py`.

**Приёмка.** Фейковый evaluator, у которого train растёт, а holdout — нет: отчёт содержит

### R7 — Нет финального подтверждающего замера · P1 · M

4. Хранить baseline-снапшот весь прогон. Сейчас `_prune_snapshots` держит только два последних,

**Приёмка.**

### R8 — Проклятие победителя в best-of-N · P1 · S

**Код.** `auto_improve.py:797` возвращает score лучшего из N одиночных замеров (`runs=1`).
`:317–318` берёт его же для лога и для проверки `--threshold`.

**Измерено.** При равных по качеству кандидатах матожидание максимума N шумных оценок равно
+0,85·sd при N = 3 и +1,16·sd при N = 5. Решение KEEP это не затрагивает — его принимает
pairwise-гейт. Но ранний стоп `optimal` и траектория в отчёте завышены.

**Сделать.** После KEEP перезамерять сохранённый артефакт независимым вызовом (`runs=2`) и
использовать этот score для лога и порога. Цена — один дополнительный вызов на KEEP, а не на
итерацию.

**Приёмка.** Все кандидаты равны, скорер шумный — порог не достигается за счёт отбора
максимума.

### R9 — Prompt и workflow оцениваются предсказанием, а не запуском · P1 · L

**Код.** `_build_llm_grader` (`auto_improve.py:598`) вместе с `agents/evaluator.md`: грейдер
читает текст артефакта и решает, *удовлетворил бы* агент ожиданиям. Артефакт не исполняется.

**Почему это плохо.** Метрика вознаграждает текст, который убедительно выглядит для грейдера.
Например, промпт, дословно перечисляющий ожидания, получает высокий score, даже если модель с
этим промптом их не выполняет. Это прямая поверхность для Goodhart.

**Сделать.**
1. Режим `--prompt-eval executed`, по умолчанию для `prompt`:
   - для каждого кейса с `prompt`/`input` артефакт выполняется как системный промпт через
     `LLMConfigManager` (новый профиль `executor`);
   - грейдер оценивает полученный ответ против `expectations` и `forbidden_expectations`,
     не видя артефакта.
2. Старый режим оставить как `static`, с явной пометкой метрики в отчёте.
3. Workflow — через агентный backend там, где он есть; иначе `static` с пометкой.

**Приёмка.**
- Фикстура «промпт перечисляет ожидания, но не производит их» получает в `executed` меньший
  score, чем в `static`.
- Отчёт называет режим оценки.

### R10 — Битый ответ грейдера превращается в оценку 0 · P1 · S

**Код.**
- `auto_improve.py:626`: при битом JSON LLM-грейдера `score = 0.0`.
- `:685`: в rubric-скорере `scores.append(0)` — одна битая оценка из двух делит score пополам.

**Последствия.**
- Битый baseline даёт 0, и первая же валидная оценка сохраняет произвольную правку.
- Битый замер кандидата даёт ложный REVERT, записанный как регресс.

**Сделать.**
1. Одна повторная попытка; затем исключение, которое R1 обрабатывает как `error` — без решения
   KEEP/REVERT.
2. В rubric-скорере исключать битые прогоны из среднего. Если не осталось ни одного —
   исключение.

**Приёмка.** Грейдер возвращает мусор — в TSV строка `error`, не KEEP и не REVERT.

### R11 — Одна модель предлагает и оценивает · P1 · S

**Факт.** В `config/llm_profiles.yaml` профили `proposer`, `grader` и `text_mutator` указывают

**Сделать.**
1. Флаги `--grader-model` и `--grader-provider`.
2. В отчёт — модели всех ролей.
3. В `SKILL.md` — рекомендация брать грейдер другого семейства моделей.

**Приёмка.** Флаги работают; отчёт перечисляет модели ролей.
