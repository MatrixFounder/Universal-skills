# Постановка: мета-скилл `design-md`

| Поле | Значение |
| :--- | :--- |
| Назначение | Скилл, обучающий агента работать с форматом DESIGN.md нативно: проектировать, проверять, применять |
| Целевой репозиторий | `Universal-skills`, каталог `skills/design-md/` |
| Аналог по роли | `skills/marp-slide/` — «формат + темы + раннер» |
| Статус | Постановка к разработке. Реализации нет |
| Дата | 2026-08-28 |

---

## 1. Задача

Формат DESIGN.md существует и стандартизован. Без скилла агент работает с ним вслепую: пишет
правдоподобный YAML, который не проходит линтер, изобретает несуществующие ключи, ставит разделы
в произвольном порядке и — главное — производит дизайн-систему, неотличимую от дефолта, ради
ухода от которого формат и заведён.

Скилл закрывает три разрыва:

1. **Синтаксический.** Агент не знает схему, порядок восьми разделов и синтаксис ссылок.
2. **Процедурный.** Агент не знает, что результат проверяется линтером, и сдаёт непроверенное.
3. **Содержательный.** Агент не отличает валидный файл от полезного.

### 1.1. Мета-скилл, а не справочник

Скилл обязан не только **проверять** оформление, но и **проектировать** его из входа трёх видов:

| Вход | Что даёт | Чего не даёт |
| :--- | :--- | :--- |
| Текстовое описание бренда или продукта | намерение, отрасль, тон, аудиторию | конкретных значений |
| Скриншот интерфейса или макета | фактические цвета, ритм, пропорции, характер | имён шрифтов, состояний, тёмной темы |
| Существующая кодовая база или CSS | фактические значения токенов | обоснования и иерархии |

## 2. Границы объёма

Принято решение: **уровень 2 плюс тонкий срез уровня 3.**

**Входит.**
- Корректная работа с форматом: чтение, авторство, правка, валидация, экспорт.
- Вкус, зашитый в ассеты: несколько готовых шаблонов, написанных с нуля и прошедших линтер.
- Правила выбора шаблона по типу продукта.
- Раздел anti-slop: перечень приёмов, которые не воспроизводить.
- Процедуры извлечения дизайн-системы из описания, скриншота и кодовой базы.

**Не входит.**
- Метод генерации палитры с нуля по цветовой теории (вывод рампы из одного цвета, гармонии,
  расчёт перцептивной равномерности). Обоснование: даёт длинный текст, который агент игнорирует,
  и качество, которое нечем проверить.
- Генерация изображений, логотипов, иллюстраций.
- Реализация компонентов. Скилл производит спецификацию, а не интерфейс.
- Собственный формат. Стандарт принимается как есть.

**Обоснование границы.** Линтер проверяет форму, но не качество. Если качество не меряется ничем,
кроме линтера, скилл сходится к «валидно и мимо». Поэтому качество поставляется ассетами, где оно
решается один раз при написании и проверяется человеком, а не выводится агентом каждый раз.

## 3. Проверенные факты о стандарте

Проверено локально 2026-08-28. Не перепроверять, но и не противоречить.

### 3.1. Формат

Источник: `google-labs-code/design.md` (https://github.com/google-labs-code/design.md),
лицензия Apache-2.0. Спецификация — `docs/spec.md` в том репозитории, конфигурация
линтера — `packages/cli/src/linter/spec-config.yaml`. Локальный клон не требуется:
`npx --yes @google/design.md@0.4.0 spec` печатает ту же спецификацию целиком.

Файл состоит из YAML-фронтматтера с машиночитаемыми токенами и markdown-тела с обоснованием.

```
version: <string>            # опционально, текущее значение "alpha"
name: <string>               # ЕДИНСТВЕННОЕ обязательное поле
description: <string>        # опционально
omitted: <string[]|OmittedSection[]>   # опционально: что файл намеренно не задаёт
colors:      { <token>: <Color> }
typography:  { <token>: { fontFamily, fontSize, fontWeight, lineHeight, letterSpacing } }
rounded:     { <scale>: <Dimension> }
spacing:     { <scale>: <Dimension|number> }
components:  { <component>: { <token>: <string|ссылка> } }
```

Ссылки на токены — в фигурных скобках, путь по дереву YAML: `{colors.primary}`, `{rounded.md}`.

Канонический порядок восьми разделов тела:
Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's and Don'ts.

### 3.2. Инструментарий

Пакет `@google/design.md` версии 0.4.0, Apache-2.0, `engines: node >=18`.
Публикуется как библиотека: экспорты `.` и `./linter` с типами.

Работает без установки. Проверено:

```
npx --yes @google/design.md@0.4.0 lint <файл>
```

Фактический вывод на эталонном примере:

```json
{
  "findings": [
    {
      "severity": "info",
      "message": "Design system defines 47 colors, 8 typography scales, 6 rounding levels, 8 spacing tokens, 10 components.",
      "rule": "token-summary"
    }
  ],
  "summary": { "errors": 0, "warnings": 0, "infos": 1 }
}
```

Команды: `lint`, `export`, `diff`, `spec`.
Экспорт: `json-tailwind` (Tailwind v3), `css-tailwind` (Tailwind v4 `@theme`), `dtcg` (W3C Design
Tokens Format Module).

Одиннадцать правил линтера: `broken-ref`, `missing-primary`, `contrast-ratio` (WCAG AA 4.5:1),
`orphaned-tokens`, `token-summary`, `missing-sections`, `missing-typography`, `section-order`,
`unknown-key`, `token-like-ignored`, `omitted-rules`.

> **К разработке.** Команда `diff` в публичной документации не описана. Её поведение установить
> по исходникам `packages/cli/src/commands/diff.ts` и задокументировать в `references/`.
> Гипотеза: сравнение двух версий файла — пригодно для поддержки системы в актуальном состоянии.

### 3.3. Ограничения окружения

- `bun` на машине отсутствует. Исходники апстрима собрать нельзя, только ставить пакет с npm.
- `node` 24.15, `python3` 3.14 присутствуют.
- Апстрим тянет `zod ^3.24`. Если скилл когда-либо будет вызывать линтер как библиотеку в проекте
  на zod 4, схемы через границу пакета не передавать.

## 4. Обязательные структурные требования

Структура скиллов в `Universal-skills` проверяется машинно: `validate_skill.py` и `analyze_gaps.py`.
Требования ниже — не стиль, а условия прохождения валидации.

### 4.1. Фронтматтер

Ровно четыре поля: `name`, `description`, `tier`, `version`.

```yaml
name: design-md          # обязан совпадать с именем каталога
description: "Use when ..."
tier: 2
version: 1.0
```

> **Дефект эталона.** У `marp-slide` во фронтматтере только `name` и `description`, из-за чего
> `validate_skill.py` на нём падает. Композицию и тон у `marp-slide` брать, фронтматтер — нет.

`description` проверяется по CSO-правилам: префикс из списка `Use when`, `Guidelines for`,
`Standards for`, `Defines`; лимит 50 слов. Если значение содержит `: ` — брать в кавычки целиком,
иначе строгий YAML-парсер отвергнет блок.

Триггеры, которые `description` обязан покрывать: `DESIGN.md`, `design tokens`, `design system`,
`tailwind config`, `deslopify`, `дизайн-система`, `фирменные цвета`, `единый стиль`,
`извлеки палитру`, `по скриншоту`.

### 4.2. Обязательные секции SKILL.md

Проверяются подстрокой в нижнем регистре, писать буквально:

- `Red Flags` — минимум три пункта в форме «мысль агента → **WRONG** → последствие».
- `Rationalization Table` — таблица «Agent Excuse | Reality».
- `Execution Mode` — строго в форме `- **Mode**: \`hybrid\``, регулярка чувствительна к формату.
- `Script Contract` — команда, входы, выходы, артефакты.
- `Safety Boundaries` — обязательна, поскольку скилл упоминает `scripts/` и перезапись файлов.
- `Validation Evidence` — мягкий лимит 12 непустых строк, целевой объём 4–6.

Порядок секций брать у `marp-slide`: Purpose → When to Use This Skill → Red Flags →
Rationalization Table → Execution Mode → Script Contract → Safety Boundaries →
Validation Evidence → … → Quality Checklist → Dependencies.

### 4.3. Каталоги и файлы

Белый список каталогов: `scripts`, `examples`, `assets`, `references`, `config`, `agents`,
`evals`, `eval-viewer`, `data`. Для `design-md` использовать четыре: `references`, `assets`,
`examples`, `scripts`.

В корне скилла **запрещены** `README.md` и `CHANGELOG.md`. Операторские заметки класть
в `scripts/README.md`.

Инлайновые fenced-блоки в SKILL.md: больше 20 строк — предупреждение, больше 60 — ошибка.
Полный шаблон DESIGN.md внутрь SKILL.md не вставлять, он уедет за лимит. Примеры вывода линтера
помечать как ` ```text `.

Целевой объём SKILL.md — **280–320 строк**. Это навигационный хребет: знания живут в `references/`.

## 6. Требования к шаблонам `assets/`

Все шаблоны пишутся **с нуля**. Копирование файлов из `examples/` апстрима недопустимо без
указания происхождения, и в любом случае нежелательно: они под другой бренд.

Каждый шаблон обязан:

1. Проходить `npx --yes @google/design.md@0.4.0 lint` с `summary.errors == 0`.
2. Содержать все восемь разделов тела в каноническом порядке.
3. Иметь заполненный раздел Do's and Don'ts, специфичный для этой системы, а не общий.
4. Объявлять в `omitted` то, что намеренно не задаёт.

Состав, минимум четыре:

| Шаблон | Назначение | Требование |
| :--- | :--- | :--- |
| `template-skeleton` | пустой каркас с плейсхолдерами | проходит lint как есть |
| `template-product-saas` | продуктовый интерфейс, плотная сетка | нейтрали ступенями, один акцент |
| `template-editorial` | контентный сайт, крупная типографика | контрастная пара шрифтов |
| `template-cyrillic` | **обязателен** | шрифты с реальным покрытием кириллицы |

**Про кириллицу.** Проверять покрытие фактически, а не по названию. Установленный прецедент:
Google Fonts отдаёт **Instrument Serif** и **Bodoni Moda** только с блоками `latin` и `latin-ext`;
на русском тексте они молча падают в системный serif. Проверенные семейства с кириллицей:
Golos Text, Onest, Inter, IBM Plex Sans, JetBrains Mono, Manrope.

## 7. Процедуры извлечения (`references/extraction.md`)

Это ядро мета-скилла. Каждая процедура обязана заканчиваться прогоном линтера.

### 7.1. Из текстового описания

Вход: описание бренда, продукта, аудитории, тона.

1. Определить тип продукта и выбрать базовый шаблон по правилам отбора.
2. Заменить токены шаблона под описание, сохранив **структуру отношений**: число ступеней
   нейтралей, отношение модульной шкалы, ритм spacing.
3. Переписать Overview и Do's and Don'ts под конкретный бренд.
4. Всё, чего описание не покрывает, объявить в `omitted`, а не выдумывать.
5. Прогнать линтер, починить находки.

### 7.2. Из скриншота

Вход: изображение интерфейса или макета. Агент читает его инструментом чтения файлов.

**Разграничение достоверности — обязательный раздел процедуры.**

| Извлекается надёжно | Извлекается приблизительно | Не извлекается |
| :--- | :--- | :--- |
| наличие и число уровней иерархии | конкретные значения цвета | имена шрифтовых семейств |
| характер: тёмный или светлый, плотный или воздушный | базовая единица ритма (4 или 8 px) | состояния: hover, focus, disabled |
| контрастность типографики | отношение модульной шкалы | тёмная тема, если снят светлый экран |
| радиусы скруглений | вес шрифтов | поведение компонентов |

**Правило.** Значения цвета, снятые глазами с изображения, недостоверны: сжатие, сглаживание,
градиенты и цветовой профиль искажают их. Поэтому:

1. Точные значения снимает **скрипт** `extract-palette` квантованием пикселей, а не агент глазами.
2. Агент интерпретирует роли: какой из снятых цветов фон, какой поверхность, какой акцент.
3. Шрифт агент **не угадывает**: предлагает два-три кандидата по характеру и просит подтвердить.
4. Всё, чего на скриншоте нет, уходит в `omitted` с явным перечислением.
5. Результат предъявляется пользователю как гипотеза с указанием, что снято, а что предположено.

> Поле `omitted` в стандарте существует ровно для этого случая. Использовать его вместо
> правдоподобных выдумок — ключевое требование к процедуре.

### 7.3. Из кодовой базы

Вход: CSS, конфиг Tailwind, файл токенов.

1. Собрать фактически используемые значения, а не объявленные.
2. Отсортировать по частоте: то, что встречается один раз, вероятно случайно.
3. Свести близкие значения в ступени, назвав расхождения в отчёте.
4. Обратная операция — `export` — позволяет проверить круговорот: DESIGN.md → tailwind → сравнение.

## 8. Anti-slop (`references/anti-slop.md`)

Тонкий срез уровня 3. Формулировать как проверяемые запреты, а не как советы.

Обязательный минимум:

- Палитра из несвязанных хексов вместо ступеней. Признак: у нейтралей нет общего уклона оттенка.
- Шрифт `system-ui` как выбор по умолчанию в файле, смысл которого — уйти от вида по умолчанию.
- Типографская шкала из произвольных чисел вместо модульной.
- Радиус, одинаковый у всех элементов.
- Раздел Do's and Don'ts, состоящий из общих истин, применимых к любому продукту.
- Акцентный цвет, используемый более чем в одной роли.
- Значения, скопированные из популярных дефолтов: перечислить конкретные хексы.

Каждый запрет сопровождать признаком, по которому он обнаруживается в готовом файле.

## 9. Контракт скриптов

Скрипты на `node` или `python3`. Зависимость от `bun` запрещена.

| Скрипт | Вход | Выход | Назначение |
| :--- | :--- | :--- | :--- |
| `lint` | путь к DESIGN.md | человекочитаемый отчёт, код выхода | обёртка над `npx --yes @google/design.md@0.4.0 lint`, разбор JSON |
| `extract-palette` | путь к изображению | список цветов с долями | достоверное снятие цвета вместо оценки глазами |
| `check-contrast` | путь к DESIGN.md | матрица пар и коэффициентов | контраст всех пар, а не только тех, что проверяет апстрим |

`check-contrast` нужен отдельно, потому что штатное правило `contrast-ratio` проверяет пары
компонентов по порогу WCAG AA 4.5:1, а осмысленная проверка — это все пары «текст на поверхности»
и уровень AAA 7:1 для основного текста.

## 11. Интеграция в репозиторий

1. Создание каркаса — `init_skill.py` согласно `docs/CONTRIBUTING.md` §4.
2. Симлинк `.agent/skills/design-md → ../../skills/design-md`.
3. Регистрация в `README.md` — в обеих таблицах.
4. Плагин генерируется, а не пишется руками: добавить `case` в `metadata_for`
   и запустить `bash scripts/sync-plugins.sh`. Категорию выбрать из существующих.
5. В `System/Docs/SKILLS.md` ничего не дописывать.
6. В CI регистрировать не требуется: матрица покрывает только `docx/xlsx/pptx/pdf/html`.
