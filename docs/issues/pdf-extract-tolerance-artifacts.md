# PDF-EXTRACT-TOLERANCE-ARTIFACTS — `pdf_extract.py` наследует два дефолта pdfplumber, которые ломают порядок маркеров списка и выдумывают строки таблиц

> **Resolved 2026-08-29.** Обе половины закрыты флагами, оба дефолта — пдфпламберовские,
> ровно как требует «Путь исправления» (новый дефолт только после прогона на корпусе).
> **A:** `--y-tolerance PT` (абсолютный, ratio здесь не работает) — на фикстуре с маркером
> 7 pt против текста 12 pt (Δ верхов 3.97 pt) значение `5` возвращает все маркеры в начало
> своих строк; на `digital.pdf` и `glued.pdf` вывод при `y_tolerance=5` совпадает с дефолтным
> символ в символ (текст и таблицы) — это зафиксировано отдельным тестом как замер
> безрегрессионности. Работает и под `--layout`.
> **B:** `--table-strategy lines|lines_strict` — `lines_strict` игнорирует незаштрихованные
> заливки. Оба симптома воспроизведены на фикстуре: страница 1 (зебра-подсветка, реальной
> таблицы нет) даёт фантомную таблицу при `lines` и ноль при `lines_strict`; страница 2
> (реальная линованная таблица + x-выровненный затенённый абзац под ней) при `lines` получает
> абзац **лишней 4-й строкой**, при `lines_strict` — ровно 3 верные строки. Реальные
> линованные таблицы под `lines_strict` не деградируют (проверено на двух фикстурах).
> Оба значения (плюс `x_tolerance_ratio`) эхом уходят в топ-левел дампа.
> Документация: `references/pdf-to-markdown.md` §3.1 (артефакт «маркер после строки»), §3.2
> (обратный случай — фантомные таблицы из заливок фона, с проверкой `stroke=False, fill=True`),
> §5, SKILL.md, `scripts/.AGENTS.md`.
> Тесты: `TestLineTolerance` (7) + `TestTableStrategy` (8), включая безрегрессионные замеры и
> отказ CLI на неизвестной стратегии (exit 2); 2 кейса в `tests/test_e2e.sh`. Мутационная
> проверка: игнорирование любого из двух флагов убивает тесты.

## Симптом

Две независимые проблемы одного корня — `pdf_extract.py` прокидывает дефолты pdfplumber
без настройки, и на реальных документах эти дефолты дают неверный дамп.

**A. Маркер списка уезжает в конец своей строки.** `text` содержит:

```
Первый пункт списка — текст строки целиком.
●
Второй пункт списка — текст строки целиком.
●
```

(строки нейтрализованы; в исходной фикстуре на их месте обычный текст пунктов —
значение имеет только форма: строка, затем осиротевший маркер отдельной строкой)

Списки приходится собирать заново вручную. На фикстуре — **32 осиротевших маркера**
на 4 страницах из 29.

**B. Залитые прямоугольники фона превращаются в таблицы.** Реальных таблиц на стр. 8–10
нет ни одной, а `extract_tables()` возвращает 3 / 6 / 3 «таблицы» — это подкрашенные врезки
и абзацы. Хуже мусора: на выводе LibreOffice затенённый абзац **приклеивается лишней
строкой к соседней настоящей таблице**, то есть в структурированный дамп молча попадает
содержимое, которого в таблице нет.

## Корневая причина

**A.** У pdfplumber `y_tolerance` — **абсолютный** (3 pt). Google Docs Renderer печатает
глиф `●` кеглем **7 pt** при основном тексте ~10–11 pt, поэтому верх бокса маркера ниже
верха строки на **3.15 pt** > 3 pt → маркер считается отдельной строкой и сортируется
**после** своей (больший `doctop`). Это ровно тот же класс дефекта, что скилл уже починил
по оси X в §3.8 (`x_tolerance_ratio`), только по оси Y и до сих пор незакрытый.

**B.** Дефолтная стратегия `lines` строит рёбра таблицы из **всех** `page.rects`, включая
`fill=True, stroke=False` — то есть из заливок фона (подсветка, затенение абзаца,
чередование строк). Любой продюсер, рисующий фон, даёт фантомные рёбра.

## Воспроизведение и доказательство универсальности

Проверено на трёх независимых продюсерах (probe-документ: абзац, список из 3 пунктов,
таблица 3×2, затенённый абзац без рамки):

| Продюсер | Кегль маркера vs текста | A: маркер оторван | B: фантомные строки/таблицы | `lines_strict` |
|---|---|---|---|---|
| Skia/PDF m148 Google Docs Renderer | 7 pt vs 10–11 pt (Δ 3.15 pt) | **да, 32/32** | **да** — 6 фантомных таблиц на стр. 9, 3 на стр. 8, 3 на стр. 10 | 0 фантомных, все реальные таблицы целы |
| LibreOffice 26.2.4.2 | 12 pt vs 12 pt | нет | **да** — затенённый абзац приклеен 4-й строкой к реальной таблице | 3 строки — верно |
| WeasyPrint 68.1 | 11 pt vs 11 pt | нет | нет (заливки совпали с границами ячеек) | без изменений — регрессии нет |

Механизм в обоих случаях продюсеро-независим; проявление A зависит от того, задан ли
маркер меньшим кеглем, проявление B — от наличия заливок фона. Оба условия массовые.

```bash
# A — на фикстуре
python3 -c "
import pdfplumber
p = pdfplumber.open('tmp16/pdf-fixture.pdf').pages[0]
print(p.extract_text())                 # '...текст пункта.\n●\n...'
print(p.extract_text(y_tolerance=5))    # '● ...текст пункта.' — верно
"
# B
python3 -c "
import pdfplumber
p = pdfplumber.open('tmp16/pdf-fixture.pdf').pages[8]
print(len(p.extract_tables()))          # 6 — фантомы
print(len(p.extract_tables({'vertical_strategy':'lines_strict',
                            'horizontal_strategy':'lines_strict'})))  # 0 — верно
"
```

## Путь исправления

1. **A** — флаг `--y-tolerance PT` (default оставить pdfplumber'ов, либо поднять до `5`
   после прогона регрессий). Замер на фикстуре: `y_tolerance=5` убирает **32/32**
   осиротевших маркера и **не меняет вывод остальных 25 страниц ни на байт**; на probe-PDF
   от weasyprint и LibreOffice вывод байт-в-байт совпадает с дефолтным. Ratio-вариант
   (`y_tolerance_ratio`) здесь **не работает**: он масштабируется от кегля самого маркера
   (7 × 0.15 = 1.05 < 3.15), нужен абсолютный подъём.
2. **B** — флаг `--table-strategy lines|lines_strict` (`lines_strict` игнорирует незаштрихованные
   заливки). Пока не зашивать `lines_strict` дефолтом: он отбросит таблицы, нарисованные
   *только* заливками, — сначала нужен замер на широком корпусе.
3. Эхо выбранных значений в топ-левел дампа рядом с `x_tolerance_ratio`, чтобы дамп остался
   самоописательным.
4. Абзацы в `references/pdf-to-markdown.md`: §3.1 дополнить артефактом «маркер после строки»,
   §3.2 — обратным случаем «фантомные таблицы из заливок фона» (сейчас там описан только
   пропуск таблиц без линовки).

## Обходной путь (до фикса)

Композиция markdown — работа агента, так что обходится глазами: маркеры восстанавливать
вручную, а каждую «таблицу» на текстовой странице сверять с `page.rects` (`stroke=False,
fill=True` → это фон, а не таблица). Проверка полноты — сверка словарного мультимножества
дампа и итогового markdown.

## Do-not

- **Не** поднимать `y_tolerance` глобально без прогона регрессий: на плотных вёрстках это
  склеит соседние строки. Флаг — да, новый дефолт — только после замера на корпусе.
- **Не** делать `lines_strict` дефолтом по результатам одного документа (см. п. 2).
- **Не** переносить это в «композиция — работа агента»: неверный порядок символов и
  выдуманная строка таблицы — это дефект *дампа*, а не вопрос суждения.
