# PDF-EXTRACT-UNMAPPED-FONT-TEXT-LOSS — документ без встроенных шрифтов теряет всю нелатиницу, а дамп выглядит здоровым

**Status:** OPEN (SEV-2 — беззвучно теряется бо́льшая часть содержимого документа; дамп при
этом отдаёт exit `0` и тысячи правдоподобных символов).
**Location:** [`skills/pdf/scripts/pdf_extract.py`](../../skills/pdf/scripts/pdf_extract.py) —
дамп не проверяет метаданные шрифтов и не имеет сигнала о непредставимом тексте.
**Related:** [PDF-EXTRACT-FIGURE-PAGE-UNFLAGGED](pdf-extract-figure-page-unflagged.md) и
[PDF-EXTRACT-TOLERANCE-ARTIFACTS](pdf-extract-tolerance-artifacts.md) — тот же мотив
«тихий отказ там, где скилл декларирует громкий»; `references/pdf-to-markdown.md` §5
(таблица кодов возврата), `references/ocr.md` (почему OCR здесь **не** спасает).
**Found:** догфуд 2026-08-29.

## Симптом

PDF, произведённый инструментом, который не встроил шрифты и писал текст небазовым для
`WinAnsiEncoding` алфавитом, теряет весь такой текст **на этапе производства файла**.
`pdf_extract.py` этого не замечает:

```
exit 0 | doc_scanned: false | scanned_pages: []
извлечено 5635 символов, из них кириллицы: 0
content-stream:  (  Product   v2 )Tj     <- на месте русских слов пробелы
```

Латиница, цифры, URL и код извлекаются нормально — то есть дамп выглядит полноценным. Агент,
собирающий markdown по предписанной §2 процедуре, выпускает **англоязычный скелет русского
документа**: заголовки без слов, пункты оглавления пустые, проза отсутствует. Ни одного
сигнала об этом в дампе нет.

## Корневая причина

Шрифты не встроены и не несут `/ToUnicode`; кодировка однобайтовая латинская
(`/WinAnsiEncoding`, base-14 `Helvetica`/`Courier`). В такой кодировке кириллических кодовых
позиций нет, поэтому производящий инструмент выбросил символы ещё при записи файла:
в content-stream'е на их месте пробелы и `\xa0`, октальных escape'ов `> 127` — ноль.

Отсюда следствие, которое важно зафиксировать: **это не дефект извлечения, а потеря данных
в самом PDF**. Текст не перекодирован — он отсутствует. Poppler рендерит те же места
пустыми. Восстановить его из текстового слоя невозможно ничем.

## Два варианта деградации (и почему это меняет выбор детектора)

| | Вариант «пустота» | Вариант «правдоподобный мусор» |
|---|---|---|
| Что происходит с непредставимым символом | выбрасывается | подменяется глифом-заглушкой (`nnnnnn 1. nnnnn`) |
| Наблюдался | в реальном документе | в синтетической пробе (reportlab, base-14 Helvetica) |
| Доля строк без единой буквы | 27 % — эвристика по форме текста **ловит** | 0 % — эвристика по форме текста **пропускает** |
| 0 встроенных шрифтов + 0 `/ToUnicode` + только WinAnsi | ловит | ловит |

Второй вариант опаснее: мусор неотличим от текста на глаз и по любой статистике формы.
Поэтому ключевым признаком должен быть **признак по метаданным шрифтов**, а не по виду
извлечённого текста.

## Воспроизведение

Замер по трём документам от трёх продюсеров — разделение полное:

| Документ | Встроенных шрифтов | `/ToUnicode` | Кириллицы в тексте | Строк без букв |
|---|---|---|---|---|
| проблемный (без встроенных шрифтов) | **0 / 18** | **0 %** | **0** | 27 % |
| Google Docs Renderer | 69 / 69 | 100 % | 38 322 | 4 % |
| Acrobat PDFMaker / Adobe PDF Library | 129 / 129 | 100 % | 17 440 | 0 % |

Синтетическая фикстура **без клиентских данных** — четыре строки, `reportlab` уже в
`requirements.txt`, бинарь в репозиторий класть не нужно (генерировать в тесте):

```python
from reportlab.pdfgen import canvas
c = canvas.Canvas(path, pagesize=(612, 792))
c.setFont("Helvetica", 12)                      # base-14, не встроен, WinAnsiEncoding
c.drawString(72, 700, "Section 1. Overview")
c.drawString(72, 680, "Раздел 1. Обзор системы")  # -> 'nnnnnn 1. nnnnn nnnnnnn'
c.showPage(); c.save()
```

## Путь исправления

1. Собирать в дамп **`fonts`** на уровне документа: `[{name, subtype, embedded, encoding,
   has_tounicode}]` — факт полезен сам по себе и не меняет поведения.
2. Флаг **`text_layer_lossy`** (рабочее имя): ни один шрифт не встроен **И** ни один не несёт
   `/ToUnicode` **И** все кодировки однобайтовые латинские. Такой документ физически не может
   нести нелатиницу — вывод детерминированный, без порогов и эвристик.
3. Предупреждение на stderr по образцу `scanned_pages`, с явной формулировкой «текст
   нелатинских алфавитов отсутствует в файле и невосстановим; нужен переэкспорт исходника».
4. **Код возврата не менять.** exit `10` = «весь документ скан»; здесь другой случай и другой
   ремонт (не OCR, а переэкспорт). Новый код возврата вводить только отдельным решением —
   таблица кодов в `references/pdf-to-markdown.md` §5 публичная.
5. `references/pdf-to-markdown.md` — дописать этот отказ в §3 и явно сказать, что OCR его
   **не** лечит: невстроенный шрифт не отрисован, распознавать нечего; OCR вернёт только
   текст, лежащий внутри растровых иллюстраций.

## Обходной путь (до фикса)

Проверять метаданные шрифтов перед доверием дампу:

```bash
python3 -c "
import pypdf
r = pypdf.PdfReader('doc.pdf')
for pg in r.pages:
    for k, v in ((pg.get('/Resources') or {}).get('/Font') or {}).items():
        o = v.get_object()
        print(o.get('/BaseFont'), o.get('/Encoding'), '/ToUnicode' in o)
"
```
Всюду `WinAnsiEncoding` + `False` в документе, который должен быть нелатинским → дампу
верить нельзя.

## Do-not

- **Не** строить детектор на форме извлечённого текста (доля строк без букв, доля пробелов):
  замерено — вариант с глифом-заглушкой такую проверку проходит насквозь.
- **Не** предлагать OCR как ремонт: глифы не отрисованы, распознавать нечего.
- **Не** класть найденный реальный документ в `tests/` как фикстуру: он содержит боевые
  Bearer-токены и внутренние endpoint'ы. Генерировать синтетическую (сниппет выше).
- **Не** пытаться «восстановить» текст маппингом байтов: в потоке на месте символов пробелы,
  восстанавливать нечего.
